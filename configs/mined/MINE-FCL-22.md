# Private pilot: adjudicate due macro questions automatically from the official dated release, and add an owner-run release fallback

Two operational gaps in the private pilot.

**1. Outcomes still wait for a human.** Frozen prospective cohort entries and autopilot-managed macro questions only get an `OutcomeProposal` (`apps/api/forecastlab_api/autopilot_outcomes.py`) that the owner must confirm. For first-release macro contracts the outcome is fully determined by the dated official BLS release, so ForecastLab should record it itself — deterministically, append-only, without calling any model and without impersonating the owner. Today an existing proposal even blocks the autopilot from re-checking a question, and if the public discovery sources are down (`autopilot.database_selection_sources()` raises) `autopilot.reconcile()` blows up and due questions are never resolved.

**2. Releases depend on GitHub Actions.** When hosted CI minutes are exhausted there is no way to run the reviewed release. The owner needs a guarded local fallback that reuses exactly the same backup / migrate / stage / smoke / promote path as `scripts/release_cloud.py`.

## Part 1 — official macro outcomes

### Storage
Add an append-only model `OfficialMacroOutcomeAmendment` in `forecastlab_api.autopilot_models`, table `official_macro_outcome_amendments` (updates/deletes refused like the other append-only autopilot records), plus an Alembic migration with revision id **`20260922_0033`** on top of `20260904_0032` (so a migrated database reports `20260922_0033` as its `alembic_version`, and fresh vs upgraded schemas stay in parity per the existing schema-parity/legacy-upgrade tests). Columns the tests read: `id`, `question_id` (FK questions), `prospective_entry_id` (nullable FK prospective_entries), `revision` (unique per question), `policy_version`, `contract_hash`, `release_event`, `status` (`"ready"` or `"exception"`), `source_url`, `source_identity_json`, `artifact_json`, `source_sha256`, `parser_version`, `measurement_json`, `outcome` (nullable 0/1), `outcome_known_at`, `retrieved_at`, `exception_code`, `exception_detail`, `created_at`.

### New module `forecastlab_api.official_macro_outcomes`
Tests patch `safe_get` and `utcnow` **on this module**, so it must call `safe_get(url, ...)` (from `forecastlab.http_client`) and `utcnow()` through module-level names. Public API:
- `SYSTEM_ATTRIBUTION` (a string such as `"system:official_macro_first_release_v1"`), used as `confirmed_by` on every outcome it writes.
- `FrozenMacroTarget` — frozen dataclass with `question_id`, `contract: ForecastContract`, `expected_contract_hash`, `macro: MacroSpec`, `release_event`, `prospective_entry_id: str | None = None`.
- `retain_official_macro_amendment(session, target) -> OfficialMacroOutcomeAmendment`
- `process_prospective_entry(session, entry_id) -> OfficialMacroOutcomeAmendment`
- `process_due_prospective_entries(session, *, cohort_id=None) -> list[OfficialMacroOutcomeAmendment]`
- `process_managed_question(session, managed: ManagedQuestion) -> OfficialMacroOutcomeAmendment`

**`retain_official_macro_amendment`** never raises for source problems; every failure becomes an `exception` amendment whose `exception_code` is a stable code:
1. Validate the frozen contract first, **before any fetch**: `forecastlab.root_event.contract_hash(target.contract)` must equal `target.expected_contract_hash` (else `frozen_contract_hash_mismatch`); the contract must still match `target.macro.template(...)` and be `approved` with `revision_policy == "first_release"`.
2. Try source identities in order: the dated BLS archive `https://www.bls.gov/news.release/archives/<family>_<MMDDYYYY>.htm` (`source_kind` `"dated_first_release_archive"`, HTML), then the dated DOL republication `https://www.dol.gov/newsroom/economicdata/<family>_<MMDDYYYY>.pdf` (`source_kind` `"dated_original_pdf_republication"`, `application/pdf`). `family` is `cpi` or `empsit`; the date is the release date in US Eastern time (e.g. CPI released 2026-08-12 → `cpi_08122026`). A response counts only with status 200, `final_url` equal to the requested URL, non-empty content and the right content type. A raised exception from `safe_get` or a non-qualifying response moves on to the next identity. If none qualifies → `official_dated_release_unavailable`.
3. Parse with the existing `forecastlab.macro_evidence.parse_release_document`, and compute the outcome by exact **decimal** comparison of the measured value with the threshold using the spec's comparison (CPI 3.4 vs `gt` 3.2 → 1; vs `gt` 3.4 → 0). Parser errors become exception codes as-is (e.g. `release_observation_period_mismatch`, `headline_measurement_unverified`, `first_release_unavailable_or_corrected`). Extend the parser so a release whose headline states **different** values for the measure fails with `headline_measurement_conflicting`, while identical repeated statements remain valid. Also export from `macro_evidence` a `FIRST_RELEASE_PARSER_VERSION` and an `archived_first_release_url(spec)` helper.
4. A ready amendment retains the raw bytes in the artifact store and records: `source_identity_json` (JSON including `source_kind`), `source_sha256`, `measurement_json` (parser output plus `value_decimal`, the measured value as a decimal string, e.g. `"3.4"`), `outcome`, `outcome_known_at` = the release's parsed publication time (equals the contract's `release_at`), `retrieved_at` = `utcnow()` at fetch, `contract_hash` = the expected (frozen) hash.
5. Append-only and idempotent: amendment ids are deterministic digests of what was recorded, so retaining the same result again returns the existing row. If a question already has a `ready` amendment and a later fetch yields different source bytes, record an `exception` with `official_release_conflicting_or_tampered` (never a second outcome).

**Retry policy.** The retryable codes are the "source unavailable" ones (`official_dated_release_unavailable` and similar transport/redirect/content-type failures). When the latest amendment for an entry/question is `ready`, or a non-retryable exception, or a retryable exception created less than **30 minutes** ago, processing returns that latest amendment without fetching. After 30 minutes a retryable exception is retried and recorded as a **new** amendment (new id, same code). Example: first attempt at T (2 fetches: BLS then DOL, both 403) → exception; immediate second call returns the same row with no fetch; at T+31 min a new exception row (2 more fetches); at T+45 min the T+31 row is returned with no fetch. Set each amendment's `created_at` explicitly with this module's `utcnow()`, and measure the 30-minute window as `utcnow() - created_at` with the same module-level `utcnow`. `retain_official_macro_amendment` itself always validates the contract and fetches: the ready / non-retryable / 30-minute skip rules apply only in `process_prospective_entry`, `process_managed_question` and `process_due_prospective_entries`. Store `outcome_known_at` and `retrieved_at` as timezone-aware UTC datetimes and return the amendment without refreshing it (the returned object must compare equal to aware datetimes).

**`process_prospective_entry(session, entry_id)`**: 404 (`HTTPException`) for an unknown entry; returns the latest amendment if no new attempt is allowed (above); the cohort must be frozen (not `draft`) and its `manifest_json["entries"]` must contain this entry's frozen `contract`; do not re-verify the cohort's `manifest_hash` here (freezing already checks it, and cohorts seeded directly may carry a placeholder hash), because the frozen contract's own hash check below is what blocks tampering; the target uses the entry's current `contract_json` as `contract` and `contract_hash(<manifest contract>)` as `expected_contract_hash` (so editing `entry.contract_json` after freezing yields `frozen_contract_hash_mismatch` without fetching); not due before the contract's resolution date. A `ready` amendment writes exactly one `ProspectiveOutcome` for the entry with `confirmed_by = SYSTEM_ATTRIBUTION` and `evidence` JSON containing `amendment_id`; reprocessing never writes a second one. Commits.

**`process_due_prospective_entries(session, *, cohort_id=None)`**: processes entries of cohorts in `running`, `awaiting_resolution` or `scored` status whose contract resolution date has passed and which may be attempted; with `cohort_id` it touches only that cohort. Returns the amendments produced.

**`process_managed_question(session, managed)`**: same flow for an autopilot `ManagedQuestion`: contract from its initial `PersonalForecast.contract_json`, macro from `managed.macro_json`, expected hash from the initial `AutopilotRun.approval_json["contract_hash"]`. A ready amendment writes a `QuestionAdjudication` (`confirmed_by = SYSTEM_ATTRIBUTION`, outcome 0/1, evidence referencing the amendment) and sets `managed.status = "resolved"`, with an inbox notification. Existing `OutcomeProposal` rows must not block it.

### Autopilot integration (`apps/api/forecastlab_api/autopilot.py`)
In `reconcile()`:
- Managed questions with an `OutcomeProposal` are no longer excluded.
- Due frozen prospective entries are processed every tick (`process_due_prospective_entries`), even while discovery is paused.
- Due managed questions call `official_macro_outcomes.process_managed_question(session, managed)` instead of `autopilot_outcomes.collect_outcome` — resolve it from the module at call time (tests monkeypatch it).
- If `database_selection_sources()` raises, still process up to two due managed questions (setting them `awaiting_outcome` first; per-question failures become inbox incidents), record a sources incident, and return `{"status": "selection_sources_unavailable", "queued": [], "gaps": [...]}`.

### Reporting / API
`prospective.cohort_report` should expose each entry's latest amendment as `official_outcome_amendment` (id, revision, status, policy_version, source_url, source_sha256, outcome_known_at, retrieved_at, parser_version, exception_code; `None` when absent); an exception never produces an `outcome`. Add `POST /api/prospective/cohorts/{cohort_id}/official-outcomes/process` (404 for an unknown cohort) returning the processed amendments and the report.

## Part 2 — owner-run release fallback

Refactor `scripts/release_cloud.py` so the pause → backup → migrate → stage → smoke → promote → complete path lives in `release_with_clients(api_client, web_client, control_request=request)`; `main()` keeps its current behaviour by building the two `VercelProject` clients and calling it.

New module `scripts/release_local.py` (importable as `scripts.release_local`) with constants `DEFAULT_BRANCH`, `REPOSITORY`, `OWNER_ID`, `TEAM_ID`, `API_PROJECT_ID`, `WEB_PROJECT_ID` and:
- `output(*args) -> str` — run a command at the repo root and return stripped stdout. All checks below go through `output` with exactly these argument tuples (tests stub `output` with a dict keyed by them):
- `preflight(approved_commit)`: requires a full 40-hex commit; `("git", "status", "--porcelain")` must be empty (else `RuntimeError("release_tree_not_clean")`); `("git", "remote", "get-url", "origin")` must equal `REPOSITORY`; `("git", "rev-parse", "HEAD")` must equal the commit; the first field of `("git", "ls-remote", "origin", "refs/heads/" + DEFAULT_BRANCH)` (format `<sha>\t<ref>`) must equal it (else `RuntimeError("release_commit_not_default_head")`); `("gh", "api", "user", "--jq", ".id")` must equal `OWNER_ID`; `("pg_dump", "--version")` must report major version ≥ 18 (`"pg_dump (PostgreSQL) 18.6"` passes). Other failures raise distinct `RuntimeError` codes.
- `database_control(path) -> dict`: performs `/internal/release/pause` or `/internal/release/complete` by calling the same `autopilot_routes.release_pause` / `release_complete` functions inside one transaction on `forecastlab_api.db.SessionLocal` (resolved at call time); any other path → `RuntimeError("unknown_release_control_command")`. On a fresh database pause reports `drained` truthy and complete reports `dispatch_paused` false.
- `validate_cloud_targets(api, web)`: each argument has `.project()` returning Vercel project details; the API project must have id `API_PROJECT_ID` and name `"forecastlab-api"`, the web project id `WEB_PROJECT_ID` and name `"forecastlab-web"`; each must have a production target id; each must have a `protectionBypass` entry whose `scope` is `"automation-bypass"`, otherwise `RuntimeError("staged_smoke_bypass_missing")` (this must be checked before anything is paused).
- `main()`: preflight `FORECASTLAB_APPROVED_COMMIT`, read the owner's Vercel token from a private local file, validate targets, configure the release environment from the API project's production env, set `FORECASTLAB_DEPLOYMENT_REVISION`, then `release_with_clients(api, web, database_control)`; print a JSON failure summary without secrets on error.

Keep existing behaviour and tests passing.
