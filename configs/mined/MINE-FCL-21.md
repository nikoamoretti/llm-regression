# Personal forecasts: bound execution by one wall-clock deadline, fix baseline outcomes, and suggest source-backed macro questions

Three problems with Personal V1 (`apps/api/forecastlab_api/personal_forecasts.py`, `personal_routes.py`, `pipeline.py`, `root_executor.py`, and `packages/forecasting/forecastlab/`).

## A. Execution is not bounded by wall-clock time

`max_wall_clock_seconds` is only checked between stages, so a slow provider response or a retry loop can run well past the profile limit and even start another paid attempt after time is up.

Add a module `forecastlab.deadline` (`packages/forecasting/forecastlab/deadline.py`):
- `ExecutionDeadline` (immutable) with classmethod `after(seconds)` → deadline `seconds` (clamped at ≥ 0) from now, and `remaining(stage) -> float`, which raises `forecastlab.errors.BudgetExceeded(stage, "max_wall_clock_seconds")` when no time is left. Use `time.monotonic()` through the module's `time` import (tests patch `forecastlab.deadline.time.monotonic`).
- `request_timeout(ledger, default, stage) -> float`: if `ledger` has a `deadline` attribute that is an `ExecutionDeadline`, return `min(default, remaining)` (raising when expired); otherwise return `default`.
- `check_deadline(ledger, stage) -> None`: raises if the ledger's deadline has expired; no-op without one.

Any ledger may carry a `deadline` attribute (tests set `InMemoryUsageLedger().deadline = ExecutionDeadline.after(5)`; `PersistentUsageLedger` should initialise it to `None` and check it when reserving).

`forecastlab.physical.run_physical_attempts` must respect the ledger's deadline:
- check it before reserving each physical attempt;
- after a **successful** response, reconcile the ledger entry first (the charged cost is kept) and *then* check the deadline, so a response that arrives after the deadline raises `BudgetExceeded(..., "max_wall_clock_seconds")` with its actual cost recorded;
- after a retryable (`TransientProviderError`) failure, the backoff sleep is bounded by `request_timeout(...)`, so once the deadline has passed it raises `BudgetExceeded` instead of sleeping or sending another attempt.
Example: deadline 5 s, the first `send` takes 6 s → exactly one attempt sent, one ledger entry, `BudgetExceeded` matching `max_wall_clock_seconds`; ledger total cost = the actual cost (0.1) on success or the reserved cost (0.2) on a transient failure; `sleep` is never called.

Wire the deadline through execution: `execute_run` and `prepare_draft` set `ledger.deadline = ExecutionDeadline.after(profile.max_wall_clock_seconds - <elapsed in prior attempts>)`; check it before persisting results; provider HTTP timeouts (OpenAI-compatible and Tavily) use `request_timeout`; `Budget` gains `remaining_seconds(stage)` used to bound macro and document fetch timeouts in the root-event executor. In the root executor a wall-clock `BudgetExceeded` should be recorded as an `execution_timeout:<stage>` evidence gap and re-raised rather than swallowed.

## B. Baseline personal outcomes are wrong

For non-root profiles (`single_model_forecaster_v1`, `three_track_forecaster`) executed on a personal forecast, the `PersonalForecast` ends with `outcome_status == "insufficient_evidence"` even though the run produced a `ForecastVersion` with an `ensemble_probability` (the session has autoflush disabled, so the new version is not visible when the outcome is derived). After `execute_run`, `outcome_status` must be `"forecasted"` and `json.loads(personal.result_json)["probability"]` must equal the version's `ensemble_probability`. The prospective `cohort_report` must only report a probability when the personal forecast's `outcome_status` is `"forecasted"`.

Also, in the root-event pipeline (`root_executor.execute_root_forecast`) pass `reasoning_effort="minimal"` on the evidence-assessment call (`schema_name="root_evidence"`) and `reasoning_effort="low"` on each root estimate call (`schema_name="root_event"`); strict-schema research-plan and evidence-extraction calls should use `"minimal"`. Bump `configs/forecast_profiles/root_event_ensemble_v1.yaml` to version 2. Outputs truncated by the model (`finish_reason == "length"`) should be treated as invalid artifacts / fallbacks, not parsed.

## C. Suggest the next source-backed macro questions (no model calls)

The owner wants ForecastLab to propose the next forecastable US macro questions from official BLS data, then turn a chosen suggestion into a normal draft for review. Selection is deterministic and must never call a model or produce a probability.

### `forecastlab.macro.fetch_latest_macro_snapshots(*, client: httpx.Client | None = None) -> dict[str, MacroSnapshot]`
Makes **one** POST to the public BLS timeseries API whose JSON body has `"seriesid"` = the BLS ids of all three `SERIES` (plus a start/end year window). The response must have `status == "REQUEST_SUCCEEDED"` and contain exactly those series, else raise `MacroDataError` (a mismatch message must contain `series_mismatch`). Monthly rows (`period` `M01`–`M12`, value not `-`/`.`/empty) are normalized with the existing `normalize_observations` (payroll monthly change in `jobs`, CPI year-over-year percent), `revision_basis="latest_observed_revisions_not_first_release"`, available/retrieved at `utcnow()` (the module-level `forecastlab.macro.utcnow`). Each snapshot's `raw_payload` is the complete, unmodified BLS response JSON (the same `{"status", "Results": {"series": [...]}}` dict for all three snapshots, series in response order). The CPI prior-year check reads the target month's prior-year row for the CPI series id from `raw_payload["Results"]["series"]`. Example: payroll levels 150000 → 150022 yield a latest observation of `22000` `jobs`; CPI 100 (2025-07) and 103 (2026-07) yield `3.0`. HTTP/parse failures become `MacroDataError`. Also let `fetch_macro` accept a `timeout` argument.

### New module `forecastlab.question_selection`
- `SELECTION_VERSION = "macro_question_selection_v1"`, `HORIZON_DAYS = 90`.
- `ScheduledRelease` (pydantic): `family: Literal["empsit", "cpi"]`, `observation_period: str` (`YYYY-MM`), `release_at: datetime`, `source_url: str`, `source_hash: str`, `checked_at: datetime`; property `event_id` = `"bls:<family>:<observation_period>"`. Validate only the `family` literal: callers (and tests) construct releases directly with placeholder URLs and hashes, so `source_url`, `source_hash` and `observation_period` are plain strings with no format checks.
- `parse_bls_calendar(html, *, source_url, checked_at) -> list[ScheduledRelease]` for the BLS annual schedule page. Table rows have three cells: date (`"Friday, September 11, 2026"`), time (`"08:30 AM"`), release (`"Employment Situation for March 2026"` or `"Consumer Price Index for August 2026"`); other releases are ignored. The reference month comes from the release text, never inferred from the release date. Times are US Eastern and converted to UTC with DST (an 08:30 release is 13:30 UTC in February, 12:30 UTC in April). `source_hash` is the 64-hex SHA-256 digest of the page. Result sorted by release time. Fail closed with `MacroDataError`: page lacks the text `All times on calendar are Eastern Time` → message containing `timezone_evidence`; no matching rows → `reference_periods_missing`; an unparseable time (e.g. `TBD`) or a reference month that has not ended before the release date → `release_invalid`; the same event listed with two dates → conflicting-dates error.
- `QuestionSuggestion` (pydantic, extra fields forbidden): `id`, `selection_version`, `question`, `macro: MacroSpec`, `reason`, `baseline: MacroObservation`, `observation_source_hash: str`, `schedule: ScheduledRelease`, `release_event`, `related_question_ids: list[str]`, `existing_question_id: str | None = None`, `existing_draft_run_id: str | None = None`. There is no probability field.
- `choose_questions(releases, snapshots, *, now, tracked=None, cohort_questions=None) -> tuple[list[QuestionSuggestion], list[str]]`. `tracked` items are `(question_id, draft_run_id_or_None, MacroSpec)`; `cohort_questions` items are `(question_id, MacroSpec)`. For each indicator in `SERIES` (`cpi` uses the `cpi` family, `unemployment`/`payrolls` use `empsit`):
  - take the earliest release of that family with `now + 10 minutes < release_at <= now + 90 days`; none → gap;
  - the threshold is the latest observation's value (`MacroSpec(indicator, observation_period=<release's period>, threshold=<latest value>, release_at=<release time>)`, default comparison/revision policy, i.e. `revision_policy == "first_release"`);
  - skip with a gap when: the snapshot is missing/empty; it was retrieved more than 24 h before `now` (or in the future); the latest observation's series id, units or seasonal adjustment differ from `SERIES`, or its `available_at` is after `now`; the latest observed period is not before the release's period, is more than ~75 days old, or lags a period whose release (in `releases`) was already out when the snapshot was retrieved; for CPI, the raw BLS payload lacks the prior-year index for the release's target month (gap text must contain `prior-year`).
  - Every indicator-specific gap string starts with `"<indicator>:"`.
  - `id` is a deterministic 64-hex digest of the selection version and the spec (independent of input order); `question` equals `spec.template(...).normalized_question`; `release_event` is the release's `event_id`; `baseline` is the latest observation.
  - `related_question_ids`: sorted ids of tracked and cohort questions about the same release event (same family and observation period; e.g. a payroll and an unemployment question share one Employment Situation event). `existing_question_id`/`existing_draft_run_id`: from a tracked entry whose spec is identical ignoring `release_at`. Cohort questions are only ever related, never "existing".
  - Sort by (already-existing last, release time, indicator name).
  Example with now = 2026-09-04 20:00 UTC, Empsit releases for 2026-08 (Sep 4) and 2026-09 (Oct 2), CPI for 2026-07 (Aug 12) and 2026-08 (Sep 11), and fresh snapshots: three suggestions in order cpi, payrolls, unemployment with thresholds `{unemployment: 4.3, payrolls: 22000, cpi: 3.0}` across two release events, no gaps. Releases within 10 minutes of now produce no suggestions.

### New module `forecastlab_api.question_suggestions`
- `SelectionSources` (pydantic): `version` (= `SELECTION_VERSION`), `checked_at`, `releases: list[ScheduledRelease] = []`, `snapshots: dict[str, MacroSnapshot] = {}`, `gaps: list[str] = []`.
- `_fetch_sources(now) -> SelectionSources`: fetch the BLS calendar page(s) for the years covered by the horizon (fixed official URL, no redirects, bounded size) and, if any releases were found, the latest snapshots; failures become human-readable `gaps`, not exceptions.
- `_fresh(sources, now) -> bool`: fresh only if version matches and `0 <= now - checked_at < TTL`, where TTL is 12 hours normally and 10 minutes when `gaps` is non-empty; and not fresh once any cached release time `r` satisfies `checked_at < r <= now`.
- `selection_sources() -> SelectionSources`: caches on disk under `settings.data_dir` (survives restarts) and serialises refreshes across threads/processes, so six concurrent callers trigger exactly one `_fetch_sources(utcnow())` call and get equal results; a later call within the TTL returns an equal cached value without fetching; after the TTL it fetches again. Use the module-level `utcnow` (tests patch `forecastlab_api.question_suggestions.utcnow`).

### API (`personal_routes.py`)
Both endpoints must call `forecastlab_api.question_suggestions.selection_sources()` and use `forecastlab_api.question_suggestions.utcnow()` as `now` for `choose_questions`, both looked up on that module at call time (tests replace them there); the simplest way is to implement the listing and draft logic in `question_suggestions` and have `personal_routes` delegate to it. `forecastlab_api.question_suggestions` imports `settings` as a module attribute (`from forecastlab_api.config import settings`) and calls `_fetch_sources` through the module global.

- `GET /api/question-suggestions` → `200` JSON with at least `items` (each `QuestionSuggestion.model_dump(mode="json")`), `gaps` (source gaps followed by selection gaps), `checked_at`, `selection_version`, `selection_cost_usd: 0`. `tracked` is built from live, non-fixture personal runs that have a macro spec (latest first): ordinary questions are tracked (the run id is passed as the draft id only while the run is `preparing` or `awaiting_review`); benchmark (cohort) questions go to `cohort_questions`. Listing creates no runs.
- `POST /api/question-suggestions/{suggestion_id}/draft` → `201` with the usual draft payload (`draft_out`). An id that is not 64 lowercase hex chars → `404`. If a draft was already created for this suggestion id (request key derived from the id) return that same run — this check comes first, so repeating the POST is idempotent. Otherwise, a suggestion id not in the current suggestions → `409`; a suggestion whose `existing_question_id` is set → `409`. Otherwise create a live draft via `create_draft(..., macro=<spec>, question_selection=<the suggestion dict>)` and, with the embedded worker, prepare it inline. The result must have `status == "awaiting_review"`, `cost_usd == 0`, `result["question_selection"] ==` the suggestion as listed, `contract["normalized_question"] ==` the suggestion's `question`, and `GET /api/forecast-drafts/{run_id}` must show the same `question_selection`. Exactly one `ForecastRun` and one `PersonalForecast`, no `forecast_run` job, no model provider built. Afterwards the listing shows that suggestion last with `existing_question_id` = the draft's question id.
- `create_draft` gains an optional `question_selection: dict | None` stored in the personal forecast's `result_json` as `{"question_selection": ...}`.
- When sources only have gaps, the listing has no items and includes the gap text, and any well-formed draft request returns `409`.

Keep existing behaviour and tests passing.
